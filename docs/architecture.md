# 客户端架构

- 状态：开发中。
- 依据：已确认的服务端与客户端边界，以及VideoSeed现有CLI、统一资源服务和渐进读取样板。

## 连接与分层

客户端通过明确的服务端地址和认证配置访问胶囊，所有权威内容写入经HTTP完成。接口唯一维护于同级服务端项目的[API契约](../../capsule-server/docs/api.md)，运行不依赖该源码项目。

| 层 | 负责内容 |
| --- | --- |
| CLI | 分层帮助、参数、输出、退出码 |
| API客户端 | URL编码、认证、请求、超时和错误转换 |
| 同步缓存 | 比较提交、下载bundle、核验和更新独立缓存 |
| 运行服务 | 读取对应提交的运行声明、准备工作目录、执行与记录 |
| SQLite日志 | 本地运行记录、旧JSON记录迁移及显式远程记录 |
| 基础设施 | 配置、路径、文件和外部进程 |

CLI和未来图形界面使用同一客户端模块。草稿与缓存状态由客户端维护，服务端负责持久内容、权限和版本校验。

## 精确同步

一次同步先取得服务端当前提交，再获取该提交的独立Git bundle。首次获取建立本地仓库，后续获取导入新对象并切换到精确提交。操作结束前核对完整提交号；本地脏缓存需要明确诊断。

缓存以胶囊为边界。下载中的临时文件与完成缓存分别存放，失败不返回已完成状态。认证值不写入运行记录或进程参数。

## 本地运行

运行限于code类别，并绑定此次同步得到的提交。在独立工作目录中取得该版本的文件，核对cap.json声明与服务端返回的版本信息，通过分离argv启动进程。

运行记录保存到客户端工作区的runs.sqlite，记录cap名称、提交号、退出码、标准输出、错误和工作位置。v1每次运行目录中的result.json逐条迁入SQLite，成功后再清理旧记录，避免丢失历史。

--log-cap显式选择一个database类别的cap，通过统一write事务创建并写入cap_run_logs。该表使用commit_id保存实际提交号。工具结果和日志写入结果分别报告，远程失败保留本地运行记录，不能据此自动重新运行工具。

首个版本支持Node内置模块脚本，并检查运行环境。带第三方依赖的工具需要后续明确的环境准备能力，现阶段遇到此类声明应给出诊断。Python和其他运行环境按同一运行接口逐步接入。

运行环境、工作目录、运行记录与胶囊缓存分别维护，临时产物不回写服务端。结果写入需经服务端内容接口并核对当前版本。

## 渐进读取

ls读取当前虚拟位置的直属cap，list按类别查询概要，entries列举真实文件。read展开指定正文及行范围，query按类别执行文本搜索或SQLite查询，write按类别处理文本或SQL事务。get与put流式获取和写入原件，数据库媒体使用media/相对路径。sync和run由调用者明确选择。
